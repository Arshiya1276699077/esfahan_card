# سامانه کارت اصفهان

این مخزن یک نمونهٔ کاملاً سمت‌کاربر (Front-end) برای مدیریت موجودی و ثبت تراکنش‌های کارت است. رابط کاربری فارسی و راست‌به‌چپ است و اطلاعات در `localStorage` مرورگر نگهداری می‌شوند.

> گزارش بازبینی: ۱۲ مرداد ۱۴۰۵ — بررسی بر اساس commit `b10df6309556c374c20fd667d95512654fb767ab`

## قابلیت‌های فعلی

- ورود کاربر و مدیر
- نمایش پنل و تاریخ/ساعت شمسی تهران
- تعیین، افزایش و کاهش موجودی
- ثبت برداشت با خط اتوبوس، مبدأ، مقصد، تاریخ و ساعت
- نمایش فهرست و خلاصهٔ تراکنش‌ها
- بازیابی نمایشی رمز عبور
- پشتیبانی از ارقام فارسی، عربی و انگلیسی در بخش‌هایی از فرم‌ها

## نحوهٔ اجرا

این پروژه مرحلهٔ build یا وابستگی محلی ندارد. برای اجرای درست، فایل‌ها را با یک وب‌سرور محلی سرو کنید و از `Login.html` وارد شوید؛ برای نمونه:

```bash
python -m http.server 8000
```

سپس نشانی `http://localhost:8000/Login.html` را باز کنید. انتخاب‌گر تاریخ در `Sabt_Riztarakonesh.html` از CDN دریافت می‌شود و به اینترنت نیاز دارد.

## نتیجهٔ بازبینی

وضعیت کلی: **نمونهٔ اولیهٔ آموزشی؛ نامناسب برای استفادهٔ واقعی یا نگهداری اطلاعات حساس.**

### بحرانی — امنیت و حریم خصوصی

1. اطلاعات ورود مدیر، شمارهٔ بازیابی و رمز در فایل‌های HTML به‌صورت صریح نوشته شده‌اند. هر بازدیدکننده می‌تواند آن‌ها را از View Source یا ابزار توسعهٔ مرورگر ببیند. این اطلاعات باید فوراً باطل/تغییر داده شوند و از تاریخچهٔ Git نیز پاک شوند.
2. احراز هویت فقط با مقادیر قابل‌ویرایش `localStorage` انجام می‌شود. کاربر می‌تواند نقش مدیر یا وضعیت ورود را مستقیماً تغییر دهد.
3. صفحات داخلی هیچ کنترل دسترسی مؤثری ندارند و با وارد کردن مستقیم نشانی باز می‌شوند.
4. رمزها و اطلاعات کاربران بدون رمزنگاری در مرورگر ذخیره می‌شوند. برای استفادهٔ واقعی، ورود، بازیابی رمز، نقش‌ها و داده‌ها باید به یک backend امن با نشست یا توکن معتبر و رمزهای hash‌شده منتقل شوند.
5. موجودی و تراکنش‌ها نیز فقط محلی هستند؛ با پاک شدن داده‌های مرورگر از بین می‌روند، بین دستگاه‌ها همگام نمی‌شوند و توسط کاربر قابل‌دست‌کاری‌اند.

> این پروژه نباید تا رفع موارد بالا با اطلاعات واقعی کاربران منتشر شود.

### زیاد — خطاهای منطقی و مسیرها

1. در `Login.html` پس از ورود، مقصد `panel.html` است اما نام فایل واقعی `Panel.html` است. روی میزبان‌های حساس به حروف بزرگ و کوچک، از جمله معمولاً GitHub Pages، ورود به صفحهٔ ناموجود می‌رود.
2. `MenhaMojody.html` اجازه می‌دهد بیش از موجودی کسر شود و موجودی منفی ایجاد گردد؛ در حالی‌که فرم ثبت تراکنش چنین کنترلی دارد.
3. افزایش و کاهش مستقیم موجودی در `AddMojody.html` و `MenhaMojody.html` رکوردی در `transactions` نمی‌سازند؛ بنابراین موجودی با گزارش تراکنش‌ها قابل تطبیق نیست.
4. خروج فقط صفحه را عوض می‌کند و مقادیر `isLoggedIn`، `userRole` و `username` را پاک نمی‌کند.
5. مسیر آیکون `/esfahan_card.png` مطلق است و در استقرار زیرمسیر (برای مثال GitHub Pages پروژه‌ای) ممکن است شکسته شود؛ مسیر نسبی `esfahan_card.png` مناسب‌تر است.
6. فایل ورودی استانداردی مثل `index.html` وجود ندارد؛ باز کردن ریشهٔ سایت ممکن است صفحهٔ مورد انتظار را نشان ندهد.

### متوسط — اعتبارسنجی و کیفیت

1. در ثبت تراکنش، placeholder ساعت ثانیه دارد، اما اعتبارسنجی فقط قالب `HH:MM` را می‌پذیرد؛ `maxlength="7"` نیز با هیچ‌کدام کاملاً سازگار نیست.
2. اعتبارسنجی تاریخ، اسفند را همیشه تا روز ۳۰ معتبر می‌داند و سال کبیسه را بررسی نمی‌کند.
3. بیشتر صفحات meta viewport ندارند؛ نمایش موبایل می‌تواند نامناسب باشد.
4. در `Panel.html` عنصر `h1` داخل `head` قرار گرفته و پایان سند نیز ساختار کامل `body/html` ندارد؛ این HTML نامعتبر است.
5. رنگ `blackbrown` معتبر نیست و مرورگر آن را نادیده می‌گیرد.
6. CSS و توابع تبدیل ارقام در چندین فایل تکرار شده‌اند و نگهداری یا رفع اشکال را دشوار می‌کنند.
7. رویدادها و کدهای JavaScript عمدتاً inline هستند؛ جداسازی در فایل‌های JS و CSS و استفاده از event listenerها ساختار را تمیزتر و تست‌پذیرتر می‌کند.
8. وابستگی انتخاب‌گر تاریخ از CDN و بدون Subresource Integrity بارگذاری می‌شود؛ در نبود اینترنت فرم تاریخ مختل خواهد شد.
9. هیچ تست خودکار، lint، قالب‌بندی یکپارچه، مجوز نرم‌افزار یا workflow بررسی کیفیت وجود ندارد.

## نکات مثبت

- رابط فارسی و RTL از ابتدا در نظر گرفته شده است.
- تبدیل ارقام فارسی/عربی و نمایش محلی اعداد پیاده‌سازی شده است.
- جدول تراکنش‌ها برای جلوگیری از تزریق HTML از `textContent` استفاده می‌کند.
- خواندن JSON تراکنش‌ها با `try/catch` انجام می‌شود و دادهٔ خراب صفحه را از کار نمی‌اندازد.
- ثبت برداشت، کافی بودن موجودی را بررسی می‌کند و تراکنش‌ها را بر اساس شناسهٔ زمانی مرتب نمایش می‌دهد.
- صفحهٔ ریزتراکنش برای جدول عریض، scroll افقی و چیدمان تا حدی responsive دارد.

## اولویت پیشنهادی اصلاحات

1. ابطال اطلاعات افشاشده، حذف اسرار از کد و تاریخچهٔ Git، و پیاده‌سازی backend امن.
2. افزودن کنترل دسترسی واقعی و خروجی که نشست را باطل کند.
3. یکسان‌سازی نام فایل‌ها و مسیرها و افزودن `index.html`.
4. تعریف یک سرویس واحد برای تغییر موجودی تا هر تغییر حتماً تراکنش متناظر ایجاد کند و موجودی منفی نشود.
5. اصلاح اعتبارسنجی تاریخ/ساعت و افزودن تست برای ورود، موجودی و تراکنش‌ها.
6. انتقال CSS و JavaScript تکراری به فایل‌های مشترک و اصلاح HTML نامعتبر.
7. افزودن راهنمای استقرار، مجوز، lint و تست خودکار.

## معماری پیشنهادی

برای ادامهٔ پروژه، رابط فعلی می‌تواند به‌عنوان prototype حفظ شود، اما داده‌های کاربر، موجودی، تراکنش و احراز هویت باید در API و پایگاه‌دادهٔ سمت سرور قرار گیرند. مرورگر فقط باید رابط کاربری و توکن نشست کوتاه‌عمر را نگه دارد؛ کنترل نقش و محاسبهٔ موجودی باید همیشه در سرور انجام شود.
